# Архитектура самостоятельного Rust coding-agent

Статус: архитектурный проект для согласования, не спецификация готовой реализации и не план работ. Дата: 2026-11-05.

Основание — [журнал решений D01–D81](agent-architecture-decisions.md). Принятые требования ниже отделены от предлагаемых технических механизмов и открытых вопросов. Исследовательские выводы не заменяют испытания выбранной композиции.

## 1. Назначение и границы продукта

Самостоятельный coding-first агент с возможностью расширения. Один Rust runtime обслуживает Termux/Linux TUI, CLI без TUI и личный headless server. Установка OMP, Bun/Node или внешнего 9router не является обязательной продуктовой зависимостью. Библиотеки, адаптированные модули и Rust-порты разрешены с соблюдением лицензий.

TUI — стандартный локальный интерфейс. CLI использует тот же agent loop без терминального renderer. Headless владеет долговременными задачами; attach подключает клиент. Скрытый обязательный daemon не нужен. Сервер личный, с несколькими сессиями/клиентами, но не multi-tenant; сетевой доступ аутентифицируется.

Android app — будущий host, не текущая поставка. Сейчас не создавать JNI/Compose/Android-service слой; бизнес-логику не связывать с TUI или POSIX UI. Имена команд и крейтов не утверждены.

По D71 поставка — один основной бинарник под Linux либо Termux, с созданием рабочих каталогов (включая конфиги/инструменты) при установке или инициализации. Ресурсы не обязаны целиком оставаться внутри бинарника. Termux/Bionic — отдельный артефакт, Linux ARM64 не заменяет его. Пути, содержимое, архитектуры и update/install protocol уточняются; D21/D27 сохраняются.

По D78 init проекта вызывается явно в каталоге уже работающего runtime: изучение проекта, подготовка инструкций/настроек без молчаливой замены существующих. Открытие каталога не требует Git/служебных файлов; это не инициализация каталогов runtime D71. Команда и создаваемые файлы уточняются.

## 2. Подсистемы и владельцы

Ниже логические границы, не требование создать отдельный crate на каждую строку.

| Подсистема | Владеет | Не должна подменять |
|---|---|---|
| Runtime | Сессии, turns/tasks/calls, lifecycle, очереди, делегирование, отмена, бюджеты | UI, provider credentials, файловый merge |
| Model gateway | Выбранные adapters, streaming, provider-native данные, model capabilities, usage и ограниченное восстановление transport | Выполнение tools и неограниченный retry всей задачи |
| Tool execution | Registry, аргументы, policy admission, запуск, outcomes и artifacts | Решение о смысловой корректности кода |
| Workspace service | Ресурсы, write ownership, isolation, snapshots, merge и restore | Пользовательскую историю Git и проверки программы |
| Code intelligence | Встроенный syntax/index/semantic анализ, версии диагностик | LSP или обещание точной семантики всех языков |
| Verification | Явные сборки/тесты/линтеры/ревью, evidence конкретной версии | Обязательный gate интеграции |
| Context manager | Сборку model input, бюджет, pruning/compaction, ссылки на архив | Durable source history и полномочия |
| Memory/skills | Scoped факты/опыт, provenance, retrieval, extraction/consolidation | Системные инструкции и изменение прав |
| Policy/config/trust | Effective settings, разрешения, проектное доверие, изменение версий | Доверие тексту из tools/web/workspace |
| Persistence/artifacts | Журнал состояния, история, большие результаты, retention/recovery metadata | Автоматический повтор внешних эффектов |
| Credentials | Доступ доверенного runtime к secrets, resolver и redaction | Агентский read API/VFS |
| Platform host | Реальные пути/cwd, процессы, PTY, сигналы и доступные возможности Termux/Linux | Универсальную OS-песочницу |
| Frontends/API | Команды пользователя, отображение, subscriptions/snapshots | Независимую копию agent logic |

По D37 UI/API используют единый контракт команд и событий: CLI/TUI внутри процесса, headless по сети; локальная работа не требует сети или отдельного сервера. Версионирование пока не выбрано. Runtime координирует сервисы; host исполняет системные эффекты. Предлагаемая граница: сервисы не вызывают renderer и не читают конфигурацию UI как источник прав.
По D62 CLI принимает запрос аргументом/stdin/файлом, выводит текст/JSON/поток событий без TUI или обязательного сервера. Данные — stdout, служебные сообщения — stderr. Успешный запуск не доказывает правильность решения; флаги, схемы и коды выхода уточняются.

## 3. Сущности и состояния

| Сущность | Назначение |
|---|---|
| Session | Самостоятельная история/диалог; project association необязательна |
| Project | Пользовательская группировка ресурсов, инструкций и настроек; не обязательно Git |
| Workspace | Конкретное файловое пространство на исполнителе; содержит репозиторий либо обычные файлы |
| Task | Цель, родитель, scope, бюджеты, состояние и результаты |
| Agent execution | Исполнение task с profile/model/context; один механизм для main и worker |
| Tool call / operation | Идентичность, аргументы, допуск, эффект и исход |
| Artifact | Версионированный адресуемый результат или большой payload |
| Snapshot / result version | Исходная файловая база либо фиксированная версия изменений |
| Verification record | Метод/команда, outcome, scope и версия проверенных входов |

Рекомендуется различать исполнение completed/failed/cancelled, отдельные waiting/parked состояния и исход операции unknown. Конкретная state machine ещё не утверждена. Завершение ответа родителя не означает завершение фоновых потомков или всей задачи. Повторный запуск отделяется от чтения сохранённого состояния.

По D61 план/список задач сохраняется в БД отдельно от текста модели: агент обновляет прогресс, пользователь просматривает/редактирует. Родитель ведёт общий план, workers — свои подзадачи. Обязательный planning mode или жёсткий workflow не вводится; состояния, связь с исполняемыми tasks и конкурентные обновления уточняются.

Project association и execution workspace — разные связи сессии. Её идентичность, история и lifecycle не зависят от проекта; ассоциация сама по себе не выдаёт permissions. По D70 у задачи один основной каталог с обычными подкаталогами; несколько внешних корней отложены. Изолированные копии workers сохраняются по D10/D11. Владение записью workspace не заменяет допуск к ресурсу и не является OS sandbox.

По D67 занятый concurrency limit ставит запуск агента в очередь до свободного места; отмена до старта доступна. Лимит, размер очереди и ожидание настраиваются, queued статус виден родителю/пользователю. Defaults, порядок, overflow/timeout и вложенные ожидания уточняются.

Лимит агентов считает активно работающих, не всех существующих/сохранённых. Provider request concurrency отделён: учитывает ограничения провайдера и нагрузку, не определяет активность агента. Точные переходы активности при ожидании инструмента/потомка и управление слотами пока открыты; прежнее предложение release/requeue не утверждено.

При исчерпании бюджета сохранить состояние, сообщить причину и позволить продолжить с изменённым бюджетом; headless recovery не создаёт бесконечный цикл автовозобновления. Предлагаемое представление — persisted waiting с причиной лимита, а не failed с автоматическим retry. Учёт охватывает шаги/retries, время, токены/оценочную стоимость, concurrency/depth, процессы и вывод; универсальный hard stop и точный финансовый cap не обещаются.

## 4. Команды, события и ресурсы

Согласовано направление VFS: управляемые данные под настраиваемым корнем, проекты по выбору пользователя, новые каталоги внутри и существующие внешние каталоги по месту. Все исходники не обязаны физически лежать в корне агента. Credentials вынесены за пределы подключаемого пространства.

Единый контракт команд и событий принят в D37. Разделение типизированных команд, событий состояния и читаемых ресурсов — предлагаемая детализация. Транспорт, wire format, конкретный VFS API, URI schemes и protocol schema **отложены**. Нельзя считать уже принятым ранее предложенный универсальный read/write facade или фиксированный набор схем.

Для headless потребуется snapshot плюс поток событий с восстановлением после разрыва. Предложение: устойчивые IDs/версии и bounded очереди; отставшему клиенту resync, а не молчаливая потеря финального состояния. Store, порядок durable/transient событий и cursors ещё выбираются. Аутентификация и session scope проверяются независимо от cursor/URI.

По D56 на текущем этапе один активный управляющий клиент на сессию. Полная multi-client реализация, наблюдатели, передача управления и конкурентный ввод отложены; несколько самостоятельных сессий не исключаются. Отключение headless-клиента не отменяет работу.

## 5. Поток обычной задачи

1. Frontend передаёт prompt/command и выбранную session; runtime определяет ресурсы, актуальные permissions и настройки.
2. Context manager собирает model input из выбранной истории, инструкций, scope и подключённой памяти. Внешнее содержимое остаётся данными, не полномочием.
3. Gateway выполняет модельный запрос. Native reasoning/replay/signatures сохраняются там, где требует provider; частичные tool arguments не запускаются.
4. Tool execution проверяет текущую policy, аргументы и ownership ресурсов, затем выполняет вызов через host/компонент.
5. Outcome и artifacts учитываются в состоянии, результат возвращается в loop. Прерванное действие не получает фиктивного success.
6. Агент продолжает, делегирует или завершает ответ. UI отдельно показывает продолжающиеся задачи.

По D76 у родителя и каждого worker собственная сохраняемая shell: cwd/env/functions/options переносятся между его вызовами, не меняя shell других агентов или глобальное состояние runtime. Это не изоляция общих файлов; D23/D27 сохраняются. Конкурентные вызовы одного агента, фоновые/интерактивные сессии, reset и crash recovery уточняются; восстановление живой shell по истории не обещается.

Новое сообщение по умолчанию — steering на ближайшей безопасной границе без прерывания текущего инструмента. Очередь отдельного запроса, параллельный side question и отмена — отдельные явные настраиваемые варианты. UX, видимость контекста side question и координация с compaction отложены.

Режим без подтверждений — default взаимодействия. Он не снимает явные deny, project trust, конфликты файлов и ограничения потомков. По D50 вопрос headless сохраняется; настраиваемый таймер до 10 минут может передать его отдельному агенту для автоответа. Таймер/авторазрешение отключаемы, initial defaults открыты. Автоответ не пользовательское согласие и не расширение прав. Опасные действия исключаются фильтром; OMP bash patterns — кандидат адаптации, но не полный анализ shell/scripts или произвольных вопросов. Точный backend, поведение при отказе и разрешение гонок ответов ещё открыты.

По D38 максимально широкий полезный набор адаптированных Rust-команд выполняется in-process. Несовместимые встроенные утилиты — через дочерний запуск того же поставляемого бинарника; внешние toolchains/программы — subprocess/PTY. Встроенный shell не заменяет компилятор или языковой runtime. Внутрипроцессный вызов требует раздельных cwd/env/I/O, отмены и лимитов, проверки process-global эффектов и exit paths. Subprocess не объявляется sandbox. Список команд, совместимость, компоненты и Termux/Bionic проверка отложены до подробного разбора.

По D59 ответ агента и headless detach не останавливают управляемые фоновые процессы. Явная остановка задачи-владельца или штатный выход runtime завершают их best-effort: graceful request, затем force после настраиваемого таймаута, по возможности с дочерними процессами. Независимое продолжение — отдельный явный режим, пока отложенный. Очистка после crash и контроль отделившихся потомков не гарантируются.

По D39 runtime поддерживает широкий набор форм tool calls и batches, доступных модели/API, выполняет их и возвращает сопоставимые результаты. Batch не равен параллельному исполнению или атомарной транзакции; policy, зависимости, budgets и workspace ownership сохраняются. Schemas, группировка и partial-error semantics отложены. Отдельный pre-execution перехват вредных/опасных команд предложен для дальнейшего разбора, без обещания полной shell-защиты.

По D40 HTTP-запросы и чтение веб-страниц встроены без обязательного curl/браузера; поиск использует настраиваемый backend. Полноценный браузер подключается отдельно по необходимости. Доступ к интернету, localhost и приватным сетям настраивается раздельно; defaults, компоненты и сетевые детали ещё не выбраны. Ограничения HTTP tools не ограничивают автоматически произвольный shell/native код.

По D41 явно переданные вложения по умолчанию направляются выбранной модели без capability-фильтрации изображений. Неподдерживаемое изображение может дать явную ошибку API; скрытое отбрасывание, текстовая подмена или смена модели не допускаются. Поддерживаются прямое изображение и отдельно настраиваемая vision-роль/модель, без автоматической маршрутизации только из-за её наличия. Необходимое protocol encoding остаётся обязанностью adapter; невозможность представить вложение — явная ошибка. Форматы, routing и хранение оригиналов ещё уточняются. Это не отправка всего workspace и не обход policy/лимитов.

Уточнение D41: ошибка отсутствия поддержки ожидается от провайдера, без специальной проверки модели заранее. Допустима прямая передача ошибки провайдера с соблюдением защиты секретов; обязательный собственный формат не задан. Общая обработка ошибок отложена до отдельного разбора.

## 6. Делегирование и фоновая работа

Основной агент выбирает организацию динамически по рекомендательным принципам; пользователь может задать роли, стадии и организацию явно. Один loop поддерживает одиночную работу, последовательные стадии, параллельные ветви и вложенную декомпозицию. Runtime supervisor детерминированно учитывает lifecycle; отдельный LLM-manager не обязателен.

Worker получает выбранный task context, scope, профиль, бюджет и ожидаемый результат, а не всю историю/credentials по умолчанию. Продолжение сохраняет собственный контекст задачи; несвязанные задачи автоматически его не наследуют. По D42 набор инструментов настраиваемый, по умолчанию все доступные и разрешённые. У worker фиксированный исходный набор роли, дополнительно настраиваемый родителем в пределах operator permissions. Показываемый набор — разрешённый для выбора; исключённый инструмент нельзя вызвать обходом по имени. Допуск конкретных аргументов/ресурсов и актуальные запреты проверяются runtime. Приоритеты ролевых изменений уточняются; model binding не расширяет полномочия.

По D36 в целом принята общая модель по умолчанию с переопределением в профиле роли или задаче. Родитель выбирает модель потомку только в пределах ограничений владельца. Автоматическая замена модели при ошибке включается отдельно; молчаливого fallback по умолчанию нет. Приоритеты и совместимость контекста при смене ещё уточняются; permissions/budgets выбором модели не расширяются.

Параметры reasoning effort/budget, лимит ответа и provider-specific настройки отложены пользователем до реализации провайдерного адаптера. Предложение об их отдельных глобальных/ролевых/task overrides не утверждено; D36 определяет выбор модели, не эти параметры.

По D51 профили ролей — Markdown с YAML-полями (описание, инструкции, модель, инструменты). Встроенные дополняются/переопределяются личными и проектными; родитель может настроить запуск worker без правки постоянного профиля. Поля, пути, reload и precedence уточняются. Профиль не активирует проектные hooks/расширения без trust/policy и не вводит обязательный pipeline.

По D68 асинхронность — обычный режим; пробуждение родителя результатом настраивается, граница ответа безопасна для доставки. Завершение, прерывание или stop только ответа родителя, новый prompt и headless detach не отменяют потомков. Явное требование родителя/пользователя прервать задачу/агента останавливает указанную ветвь best-effort. Выход/падение runtime прерывает агентское исполнение; resume по D16/D47 — отдельная операция. Потомки входят в общий budget, выполненные эффекты не откатываются. Отключённый wake не удаляет результат; default и UI-команды уточняются.

По D49 приняты parent/worker сообщения в обе стороны и настраиваемые peer messages, сохранение сообщений в БД и инъекция между шагами без прерывания инструмента. Ожидающего будить по настройке; отменённому требуется явный resume. Сообщение не отменяет работу и не расширяет права. Durable pending delivery и ack semantics уточняются; принятие runtime не означает model-processed. У original OMP mailbox in-memory, поэтому его IRC bus не доказывает требуемую сохранность очереди после restart.

По D79 завершение worker — единый поток: финальный ответ по шаблону, сохранение результата/контекста, уведомление родителя с ответом, ID агента и адресом контекста в локальной VFS. Конкретный шаблон и адреса выбираются при реализации; wake/delivery — D49/D68. Приоритет готовым компонентам и адаптации доноров, не раздельным продуктовым механизмам для частей одного результата.

Возврат результата, его принятие и файловая интеграция различаются. Родитель владеет общей задачей и может вернуть того же worker на доработку. Пока runtime жив, результаты доступны без TUI; при process death восстановление требует durable состояния. Peer teams и handoff владельца разговора не входят в обязательный набор.

## 7. Workspace, изоляция и интеграция

Чтение допускается параллельно. Запись общего workspace — у одной сессии; правило координирует отдельные CLI/TUI/headless процессы. При занятой записи по умолчанию предлагать isolation. Это кооперативная защита от собственных writers, не запрет внешнего редактора.

Для изоляции по умолчанию захватывается snapshot фактических файлов, включая допустимые незакоммиченные изменения, без обязательного коммита и изменения пользовательских HEAD/index. Clean/commit-only режим может задаваться правилами. Если корректная база не получена, не заявлять неполный снимок полноценным.

По D44 правка привязывается к прочитанной версии файла: изменение файла требует конфликта и перечитывания вместо слепого применения. Параллельные пользовательские изменения не затираются. Конкретный edit backend и защита окна между проверкой и записью уточняются по исходникам оригинального OMP; его механизмы не считаются автоматически эквивалентными проверке полной версии.

По D66 планируется встроенная фильтрация путей; объединять или разделять фильтры обнаружения/доступа — решить позже. Defaults, ignore sources, overrides и охват операций открыты. Это не обещание ограничения произвольного shell/native кода.

Source audit original OMP зафиксирован в D44: hashline использует короткий тег нормализованного всего файла и snapshots, допускает safe recovery stale edits; write не имеет такого version guard. Короткий тег не уникальная версия raw bytes, а staging не CAS/многофайловая транзакция. Кандидат — адаптировать pi-edit с отдельным строгим version guard/writer, не объявлять original готовым исполнением D44. Это предложение механизма, не утверждённый backend.

По D60 изменения отображаются по операциям агента внутри runtime (родитель, workers, форматирование), с задачей/источником; интеграция не дублирует учёт исходной правки. Общий workspace diff не заменяет учёт авторства. Чужие изменения не присваиваются агенту; захват произвольных shell/внешних writes требует отдельного механизма и явной отметки неоднозначности. Журнал/UI уточняются; просмотр не выполняет коммит/откат.

Пользовательские коммиты — только по просьбе или настроенному workflow, с отбором относящихся к задаче изменений. Неоднозначные смешанные правки не захватывать молча; внутренние snapshots/checkpoints хранить отдельно от пользовательской Git-истории. Требование clean/commit-only само по себе не разрешает автоматически коммитить всё дерево.

Интеграцию выполняет код: base snapshot / текущая цель / фиксированный worker result. По умолчанию автоматическая; deferred сохраняет workspace и допускает повторные правки того же worker. Возобновление до merge инвалидирует старую готовность; одновременно менять интегрируемую версию нельзя.

По D75 карта проекта должна давать максимально полезный обзор структуры и доступных символов/сигнатур, не только дерево файлов. Возможности зависят от встроенных backends D35. В модельный контекст идёт ограниченный бюджетом обзор, остальное доступно по запросу; карта не заменяет актуальное чтение D44. Фильтры D66 и актуализация после изменений сохраняются. Backends, отбор, кеширование, частота и defaults уточняются; производительность ещё не проверена.

Применение сериализовано и перепроверяет актуальность цели; при её изменении пересчёт имеет конечный лимит. Невозможность захвата базы, ошибка механизма и merge conflict — разные outcomes, ни один не разрешает перезапись данных ради успеха. Семантика неразрешённых конфликтов — вернуть родителю с сохранёнными вариантами; никакого принудительного ours/theirs/union. Родитель исправляет либо делегирует, после чего runtime повторяет merge. Чистое слияние означает только merged.

**Открытая механика:** write ownership и auto-integration должны использовать один координатор. Изолированный worker не получает самостоятельной записи в target; integration выполняется от имени владельца цели либо ждёт его допуска. Точные lease granularity, crash recovery и транзакционность многофайлового применения требуют проектирования. Самовольное применение поверх активного target writer недопустимо.

## 8. Диагностика и проверки — отдельно от merge

LSP не планируется. Нужны встроенные анализаторы из готовых компонентов, модификаций и Rust-портов. Уровни: синтаксис, индекс/символы, языковая семантика. По D35 направление — максимум доступных популярных языков; конкретные backends, перечень, глубина и состав первой поставки разбираются позже. Ограничение старта только AST/индексом не принято. Одинаковая глубокая семантика для всех языков не обещается; fallback не выдаётся за точную семантику.

По D45 форматирование — управляемая работа, допускающая фон параллельно агентам и доставку результатов в их контекст на безопасной границе. Режим (фон, после агента, в конце работы) и поведение задаются настройками/конфигом; default и набор встроенных/внешних форматтеров ещё не выбраны. Применение — запись с workspace ownership и version guard: stale результат не затирает свежие правки, форматирование обновляет версию файла. Ошибка явно сообщается, не откатывая прежнюю правку автоматически. Фоновая работа не разрешает одновременную неконтролируемую запись; проектные команды требуют trust/policy.

Направление фоновой диагностики: после изменений анализатор получает версию входов; новые diagnostics доставляются на безопасной границе loop, устаревшие отбрасываются, повторы ограничиваются. Это предлагаемая внутренняя модель, не перенос OMP LSP-клиента. Автоисправление и форматирование не скрытый эффект диагностики.

По D46 сборка и тесты — явные проектные этапы, не фоновые анализаторы. Запуском управляют пользователь, родитель или исполняющий агент, в том числе через явно заданный ими порядок работы. Триггеры форматтера/анализаторов не распространяются на них автоматически. Проектный lint — также явная команда; встроенная диагностика отделена. Асинхронное исполнение явно запущенной команды допускается. Outcome относится к проверенным входам; timeout/unavailable/cancel не pass. Merge не требует этих проверок по умолчанию; явно заданный workflow может связать операции.

## 9. Контекст, память и skills

Reference — original OMP: configurable compaction, ручной/автоматический запуск, safe boundaries, provider replay/cache и optional speculation. Методы и порядок не скопированы как обязательные defaults. Подробнее [source research](omp-compaction-research-2026-11-05.md).

Продуктовая цель — полный архив отдельно от сокращаемого model view. При реализации pruning сохранять raw данные до destructive projection, если они входят в обещанный архив. Retention/явное удаление могут ограничивать восстановимость, об этом сообщается. Native opaque history зависит от provider; vision archive требует подходящей модели и оценки качества.

Фоновая compaction привязана к snapshot и применяется только при актуальности; no-progress и ошибки не вызывают бесконечные retries. Входные сообщения/результаты не теряются при смене projection. Точные thresholds, дедлайны и взаимодействие steering/compaction открыты.

Memory — явные записи плюс настраиваемое извлечение опыта и skills. По D53 общая память содержит предпочтения владельца и переносимый опыт, проектная — знания проекта. Записи сохраняют источник, различают указание пользователя и вывод агента; доступны просмотр/исправление/удаление. Память — контекст, не новые инструкции или права. Удаление записи не удаляет автоматически её старые копии из истории. Извлечение, поиск и производные summaries требуют детализации. Изменение весов модели не входит в согласованный объём.

По D52 skills представлены общим настраиваемым каталогом: metadata (название/описание) сначала, полный текст по необходимости или при явном preload для роли/задачи. Доступен ручной вызов. Чтение skill не запускает scripts, не выдаёт permissions/trust. Пути, discovery и duplicate precedence уточняются.

По D58 пользовательские команды реализуются как вызов skills, без отдельной системы prompt templates. Детали отложены: синтаксис, аргументы и конфликты имён со встроенными командами не выбраны. Сам вызов не запускает вложенный shell автоматически.

## 10. Конфигурация, trust и credentials

Слои: defaults, пользовательский конфиг, проектный уровень, запуск, сессия. Инструкции LLM отделены от runtime settings; hooks/автоматизация активируются отдельно. Политика merge списков/прав и точные форматы ещё не выбраны.

По D48 LLM-инструкции разделены на общие для всех агентов, проектные (все агенты проекта либо только родитель, настраивается) и частные (роль/конкретный агент/задача). Вложенные проектные правила применимы к своему подкаталогу. Задача и выбранный контекст передаются отдельно. Уровни не расширяют runtime permissions; форматы, discovery, приоритет противоречий и default проектной области ещё открыты. Исключение AGENTS.md из worker context по имени не принято.

По D69 настройки доступны через TUI-конфигуратор (выбор, ввод, комбинированные элементы), текстовый конфиг с подсказками значений и read-only/изменяющие команды CLI/headless. Формат файла, UI и команды уточняются. Все интерфейсы разделяют правила проверки и слои D15, применение — D29; обычный просмотр не раскрывает secrets. Отдельная диагностика компонентов пока не утверждена целиком.

Личные явно включённые расширения загружаются автоматически. Project hooks/MCP/plugins требуют trust или operator rule; открытие репозитория не активирует их молча. Все три пути расширения предварительно предусмотрены: Rust, внешние команды/MCP, пользовательские extensions. Их runtime и isolation не выбраны.

По D54 принято направление полной поддержки MCP как клиента, не только вызовов tools. Конкретная версия/capability matrix и остальные детали отложены. Безопасность проверяется перед действиями, включая запуск stdio-сервера до его исполнения, не лишь tools/call. D20 trust/policy сохраняется; MCP не обязателен для базовой работы. Остальные пути P01 остаются предварительными.

По D57 система hooks входит в согласованный объём; события, формат/runtime, порядок и контракты исполнения/ошибок разбираются позже. Предложенные детали не утверждены целиком. Trust/policy D20 и явные проектные этапы D46 сохраняются; остальные неутверждённые механизмы P01 остаются предварительными.

Новые настройки UI применяются сразу, execution settings — на безопасных границах, текущие запреты — перед новым действием. Активный процесс не обрывается молча от reload. Effective versions фиксируются; границы атомарного обновления и invalid config остаются открытыми.

По D80 SQLite сохраняет сессии/агентов, ветвящуюся историю, намерения/исходы calls, ожидающие сообщения и метаданные внешних артефактов. Основа — адаптация Goose sessions/messages и OMP parentId; точная схема открыта. Обычная запись с ожиданием результата, без разрешения на сохранение и обязательного TurnAck-протокола. Compaction меняет model projection, не исходный архив в рамках retention.

По D81 файловый артефакт сначала записывается во временный файл и публикуется без перезаписи чужого объекта, затем ссылка фиксируется в SQLite. Донор — Rust agent_output форка; orphan после сбоя обнаруживается обслуживанием, SQL/file atomicity не обещается. Неполный сбор помечается явно, excerpt/full read — D43. VFS-контекст worker читается из истории без обязательного дублирования диалога текстовым файлом. Имена/URI, streaming и cleanup уточняются.

Secrets — отдельный физический каталог вне VFS, без подключения через aliases/ancestor/symlink; доступ доверенного runtime, не model tools. Master key/encryption/unlock и unattended headless отложены. Same-UID shell/native plugin способен обойти VFS: без выбранной OS/executor boundary нельзя обещать принудительную секретность. Env/логирование/экспорт требуют фильтрации, а не только скрытия значения в UI.

Headless использует собственные credentials; подключение клиента не передаёт его provider credentials автоматически.

## 11. Восстановление, ветвление и обслуживание

Внутренние recoverable errors обрабатываются автоматически в пределах budgets. Restart/crash локального CLI/TUI предлагает resume, но не исполняет автоматически. По D47 headless default — автоматическое продолжение незавершённых задач после сбоя/перезапуска; ручной режим и поведение настраиваются. Explicit stop/cancel не интерпретируется как сбой для auto-resume.

По D31 локальный CLI после ответа родителя остаётся жив, пока работают потомки; явный выход останавливает локальный runtime best-effort. Для продолжения после отключения клиента — headless/attach, без скрытого daemon. В БД сохраняются последний ход и состояние каждого агента, включая родителя, во время работы, не только при выходе. Завершённое, прерванное/частичное и unknown tool outcome различаются. Последний ход не заменяет полную историю. Backend принят в D32, границы записи — в D33; восстановление живого процесса и неперсистированных данных не обещается.

По D32 состояние, история и метаданные хранятся в SQLite; большие артефакты и файловые snapshots — отдельно на диске со связью через метаданные. Отдельного сервера БД нет. Rust-библиотека, схема и число БД не выбраны; протокол согласования БД с внешними файлами при сбое проектируется отдельно, SQLite transaction не распространяется на файловые операции. Secrets не входят в обычную историю/артефакты.

По D43 в целом принят вывод больших tool results через артефакты: полный результат сохраняется, модель получает ограниченный фрагмент, отметку сокращения и ссылку. Доступны диапазоны и поиск; пороги настраиваются, LLM-пересказ не обязателен. Secrets, бюджеты и retention сохраняют силу: если сбор/сохранение ограничены, артефакт явно помечается неполным, а не выдаётся за полный результат. Пороги и выбор фрагмента уточняются.

По D33 родитель и workers сохраняют намерение tool call перед запуском, результат — после завершения; завершённое сообщение — сразу, незавершённый поток — периодически с настраиваемым интервалом. Штатный выход сбрасывает оставшиеся записи. После сбоя последний несохранённый фрагмент может быть потерян; намерение без результата означает необходимость выяснить исход, а не разрешение повторить действие. Конкретные durability settings ещё открыты; поведение при ошибке записи принято в D34.

По D64 изменение/повторная отправка старого сообщения создаёт новую ветку, сохраняя исходную историю, без автоматического отката файлов. Restore выбирается отдельно по D17; UI и взаимодействие с активными задачами уточняются.

По D34 ошибка сохранения приостанавливает новые tool calls и model requests с явной причиной, без скрытого перехода в режим без истории. Уже начатые действия не повторяются; после восстановления записи продолжение учитывает их реальные либо неизвестные исходы. Достаточно базового error path, отдельная сложная подсистема для этого сценария не нужна.

По D47 runtime кодом определяет статус вызова из durable записей и контракта инструмента; обязательного LLM-анализа исхода нет. Если результат допущенного к запуску вызова не сохранён, факт/исход эффекта не подтверждён. Повтор или автоматическая проверка разрешаются контрактом инструмента; без надёжного восстановления возвращается явный прерванный/неподтверждённый исход, не success и не слепой повтор. Replay журнала не запускает tools; credentials, permissions и workspace сверяются заново. Exactly-once произвольного shell/network действия не обещается; state machine и retry contracts уточняются отдельно.

По D55 экспорт/импорт — файл сессии/истории, не обязательный пакет workspace/checkpoints. Отдельный аудит содержимого не требуется; credential store не входит в историю/экспорт, redaction сохраняется. Секрет, вручную вставленный в сообщение/вывод, всё же может оказаться в истории. Импорт проверяет структуру/версию формата, не исполняет сохранённые вызовы; актуальные права проверяются при исполнении. Формат и внешние artifact references уточняются.

Conversation branch, workspace checkpoint restore и совместное действие разделены. Restore не переписывает чужие изменения молча и не отменяет remote side effects. Согласование restore с живыми writers обязательно; механизм ещё открыт.

Cleanup triggers: во время сессии, после выхода, по сроку, вручную. Активные/pinned/conflicted/deferred данные не считаются свободным мусором. О полувременных результатах напоминать во время/при выходе. Headless detach не равен session end; напоминания без клиента сохраняются как состояние для последующей доставки, точный UX открыт.

## 12. Наблюдаемость и режимы UI

Два переключаемых уровня подробности с настраиваемым составом данных. Точные поля, клавиши и начальный уровень отложены. CLI и API отображают те же реальные outcomes, а не отдельную логику успеха. Подробность не изменяет permissions и не разрешает хранить secrets/raw payload без политики.

По D63 TUI показывает список агентов, статусы и текущие действия; позволяет открыть историю сообщений/tools любого агента и вернуться к родителю без остановки работы. Просмотр не перенаправляет пользовательский ввод автоматически; сообщение выбранному агенту отправляется явно. Клавиши и компоновка отложены.

По D73 доступны список сессий (название, проект, время, состояние), фильтры, поиск по истории и явное открытие/продолжение через TUI/CLI/headless. Поиск не инжектирует найденные диалоги в контекст автоматически. Индекс, охват и UI уточняются.

Различать завершённый ответ, активный task, фоновую работу, ожидание конфликта, неопределённый исход операции и лимит бюджета. Финальный ответ модели не является единственным источником состояния runtime.

По D74 локальный инспектор показывает включённые в контекст инструкции, сообщения, skills, tool results и занимаемое место. Оценка токенов отделена от provider usage, secrets скрываются; недоступные через API рассуждения не обещаются. Отображение и экспорт уточняются.

По D77 локальный учёт показывает все доступные метрики вплоть до каждого модельного запроса, не только агрегаты. Оценки и provider/measured данные различаются, неизвестные не выдумываются. Долговременное сохранение рассматривается; цены, поля и остальные детали отложены до реализации провайдерного адаптера. Внешняя телеметрия D72 не вводится.

По D72 предусмотрены диагностические логи и отправка отчётов об ошибках, без usage/analytics телеметрии или общего экспорта активности. Secrets и чувствительные данные защищаются; credentials, история, файлы и полные tool payloads не включаются автоматически. Состав/получатель отчёта, ручной/автоматический режим и retention уточняются.

По D65 в целом приняты настраиваемые уведомления о завершении, ошибке и необходимости ответа: TUI-индикатор, необязательный звук, опциональные внешние hooks/notifier. История/файлы автоматически наружу не отправляются. Доставка — сигнал внимания, не источник состояния задачи; каналы, payload и defaults уточняются.

## 13. Заимствования и собственный код

| Область | Предпочтительная исходная точка | Условие |
|---|---|---|
| Edit/search/AST/VFS/shell/VCS | Original OMP Rust engines | Выбранные host APIs/features, dependency graph, Termux/Linux сборка |
| Loop/providers/supervisor | Rust-форк после сравнения original semantics | Не тащить весь CLI как обязательный framework |
| Gateway | Готовые Rust adapters либо выбранный Rust-порт 9router | Tool/reasoning/replay/headers/errors сохраняются, один владелец retry/refresh |
| Repo map/compaction | Aider, OMP, OpenCode, OpenHands | Конкретные алгоритмы, не весь runtime и не скопированные числа |
| Memory/skills | OMP/Mem0 и другие проверенные срезы | Scope/provenance/delete/лицензии; полного backend parity не предполагать |

## 14. Первая реализация и целевое развитие

**Согласован текущий продуктовый объём:** Termux/Linux TUI/CLI, личный headless, coding-first, свой runtime, permissive default policy, динамическое делегирование, изоляция/merge, настраиваемое встроенное tooling. Android и multi-tenant вне текущей реализации.

**Предлагаемый первый проверяемый срез, не утверждённая урезанная поставка:** один полный путь prompt → модель → tools → persisted result в локальном и headless режимах; один worker lifecycle; snapshot/merge без обязательного коммита; отдельные diagnostics/verification; ограниченный provider/auth набор. Это техническая опора, а не замена согласованных возможностей пустыми интерфейсами.

Стартовый provider/auth набор принят отдельно (D30): только OpenAI-compatible API с настраиваемым base_url, ключ из переменной окружения runtime. Anthropic-specific adapter, OAuth и credential-store backend — не в первой реализации. Headless использует своё окружение; ключ не наследуется массово subprocess и не попадает в историю/логи. Имя переменной и API dialect/endpoint ещё не выбраны.

Memory/learning, широкий provider каталог, точная semantic поддержка языков, plugin runtime, развитые workflows и дополнительные compaction backends остаются частью целевого развития; их границы первой поставки пока не определены. Не называть отложенные функции реализованными и не выдавать интерфейс без поведения за готовую подсистему.

## 15. Открытые решения, влияющие на реализацию

| Решение | Почему требуется | Что уже известно |
|---|---|---|
| OpenAI-compatible API dialect/endpoint | Определяет stream/tool/replay контракт | Один стартовый адаптер, настраиваемый base_url, ключ из env (D30) |
| Schema/store и crash protocol | Durable tasks, restore и multi-process coordination | SQLite и внешние файлы приняты (D32); чтение истории не повторяет эффекты |
| Workspace snapshot/merge backend и ownership | Dirty/non-Git, integration, внешние edits | Snapshot default; конфликты родителю; merge отдельно от tests |
| Секреты и граница исполнения | Same-UID произвольный код обходит VFS | Отдельный vault; crypto/OS boundary ещё не выбраны |
| Встроенные code backends первого среза | Реальная portability и набор native dependencies | Без LSP; языки/глубина пока отложены |
| Бюджеты и enforcement | Определяют допуск, измерение и остановку операций | Потомки учитываются суммарно; лимит сохраняет состояние, не зацикливает resume |
| Будущий extension runtime | Может изменить trust и dependency graph | Три пути предварительны; project trust обязателен |
| Durable progress агентов | Последний ход родителя и workers должен переживать остановку runtime | SQLite (D32), границы записи D33; интервал и crash-consistency открыты |

CLI lifecycle согласован в D31; точные сигналы, timeout штатной остановки и UX ожидания требуют детализации. Отложенные форматы/клавиши не мешают согласовать логическую архитектуру, но соответствующие механизмы нельзя надёжно реализовать до уточнения их контрактов.

## 16. Проверяемые архитектурные сценарии

Это критерии будущей проверки, не проведённые тесты.

- Без installed OMP/Bun/Node/9router выполнить прямой provider tool loop и открыть сохранённую session.
- TUI/CLI/headless используют одинаковые state transitions; потеря headless-клиента не отменяет задачу.
- Parent answer завершается, worker продолжает; explicit cancellation блокирует новые действия потомков и учитывает неостановленные операции.
- Два runtime конкурируют за target; одновременно writer один, isolated merge не обходит ownership.
- Из dirty/non-Git base создать изоляцию, внести изменения, слить без потери пользовательских правок; конфликт не повреждает target.
- Deferred worker дорабатывает результат; старая версия не интегрируется как новая и старое review не становится pass новой revision.
- Диагностика stale revision не подмешивается как актуальная; merge работает независимо от запуска тестов.
- Compaction сохраняет task/scope/pairing, архив читаем согласно retention; смена provider не использует несовместимый opaque replay.
- Restart предлагает/выполняет resume согласно mode policy, но не повторяет unknown external effect автоматически.
- Project instructions/config не включают executable extensions без trust; reload не позволяет проектным данным расширять operator permissions, новые запреты проверяются перед каждым новым действием, включая действия потомков.
- Vault отсутствует в VFS/exports/logs; same-UID угрозы не объявляются закрытыми без отдельного проверенного механизма.
