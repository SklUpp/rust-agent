## 1. Общий контракт исследования

Основной агент владеет дизайном, связями подсистем и итоговой рекомендацией. Scouts находят и проверяют доноров, APIs, лицензии и ограничения. Независимый reviewer проверяет синтез, не подменяет его новым дизайном.

Для каждой подсистемы получить одну карточку:

1. Требования из журнала: принято / предварительно / отложено.
2. Доступная основа: original OMP сначала, Rust-форк отдельно, затем дополнительные доноры по конкретному пробелу.
3. Точные версии, source symbols, LICENSE/NOTICE и зависимости; отсутствие готовой библиотеки не исключает extraction/port.
4. Решение parent: взять, адаптировать, перенести на Rust, переписать либо не включать; почему существующего кода недостаточно.
5. Владельцы состояния, входы/выходы, cancellation, storage и trust boundaries; реальные несовместимости доноров.
6. Проверяемые сценарии, ограничения source evidence и открытые развилки для пользователя.

Не подключать несколько полных agent frameworks. Не задавать пользователю выбор, разрешаемый исходниками или уже принятыми решениями. Не проводить benchmark без реализации и не называть source audit runtime proof.

## 2. Пакеты

| Пакет | Совместно исследуемые части | Требуемый результат |
|---|---|---|
| A. Состояние и контекст | SQLite sessions/history/branches; tool intent/outcome; mailbox/completion; artifact publication/VFS; context builder, compaction projection и provider replay boundaries | Единая схема данных и потока сохранения/восстановления; без двойного authoritative JSONL и без протокола разрешения записи |

Исполнение и безопасность | Tool/batch scheduler; active-agent и provider лимиты отдельно; per-agent shell/builtins; subprocess/PTY; workspace ownership, isolation/merge, version-checked edit; filters, dangerous-command guard, env/credentials и preexec boundaries | Схема допуска и ресурсов, точные engines/host adapters, пределы принудительных гарантий Linux/Termux |
| C. Providers и MCP | Первый OpenAI-compatible adapter, stream/call/image payload integrity; ошибки/cancel/retry seams; MCP SDK и capability matrix | Донорская карта адаптеров и единый вход tools/results; конкретные отложенные endpoint/auth/reasoning решения остаются открытыми |
| D. Знания и расширения | Code intelligence/repo map; memory/extraction/provenance/delete; skills/roles/instructions; hooks и расширения | Состав готовых компонентов, совместимые контракты scope/config и список деталей для этапов реализации |
| E. Продуктовая оболочка | Общий runtime API; CLI/headless/single active client; TUI/configurator/agent views; установка каталогов, Linux/Termux packaging; diagnostics/error reports | Реальный composition/dependency graph, границы frontend, native features и матрица будущих проверок |

Для A использовать уже собранные source-факты Goose session schema, original OMP entries/context builder и Rust output publisher. Для B использовать уже измеренный source cut и shell/process seams. Не повторять поиски ради наполнения таблицы.

В D исследовать максимальное полезное покрытие языков без молчаливого ограничения AST-only. Для отложенных подробностей фиксировать доступных доноров и ограничения, не утверждать окончательный язык/plugin runtime/формат hook.

В E фиксировать TUI-donors и seams, но не разрабатывать отложенный UX @files, клавиши, темы или обновление продукта.

## 3. Порядок и параллельность

1. Составить реестр имеющихся доказательств по A–E: что достаточно, что устарело/противоречиво, где реальный пробел. Никакого повторного полного обзора OMP.
2. Исследовать A и B независимыми read-only lanes: они определяют ядро контрактов. Внутри пакетов параллелить только независимые source-срезы; основной агент сводит общие ID/ownership/storage границы.
3. После фиксации рабочих контрактов исследовать C, D, E параллельно, передав им результаты A/B. Подсистемы не выбирают второй store/loop или собственные противоречащие scopes.
4. Свести общий граф зависимостей и поток task → model → tools → persistence → worker result → frontend. Проверить restart/cancel/storage-error/policy-reload и native portability сквозным образом.
5. Независимый correctness/security review; исправления делает основной агент. Пользователю вернуть один сводный пакет решений, а не отдельный вопрос о каждой функции.

Число scouts ограничено текущими runtime slots; большие локальные builds запрещены. Исследования read-only; основные документы редактирует один parent. Сетевые запросы пакетировать, где независимы.

## 4. Когда спрашивать пользователя

После пакета — только материальные развилки с последствиями: несовместимые модели исполнения, лицензии, обязательные внешние зависимости, невозможность выполнить принятую гарантию либо существенное изменение продуктового поведения. На каждый вопрос дать источники, рекомендуемую реализацию, альтернативу и риск.

Исследовательские решения, не меняющие контракт, основной агент принимает консервативно и указывает в синтезе. Явно отложенные темы не возвращать мелкими вопросами: разобрать на соответствующем этапе реализации или при доказанном блокере.

## 5. Итоговый комплект

- Карта подсистем с одним основным донором и дополнительными адресными срезами.
- Реестр pins/licenses/native dependencies с границами проверки.
- Схема данных и ownership, публичные/внутренние контракты без преждевременного crate-per-type.
- Список конкретного extraction/port/rewrite и миграции callers, без compatibility shims.
- Вертикальный порядок будущей реализации и smoke/crash/cancel сценарии Linux/Termux.
- Короткий список действительно оставшихся решений пользователя, отделённый от уже принятого.

Не создавать код, stubs, install scripts или неисполненные тесты в рамках этого исследования. Сборочная/поведенческая проверка после отдельного разрешения реализации; сейчас — source и документальная проверка.
